# Оценка воздействия на защиту данных (DPIA)

## 1. Назначение документа

Оценка воздействия на защиту данных (Data Protection Impact Assessment, DPIA) — это процесс, который помогает организациям выявить и минимизировать риски для защиты персональных данных (ПДн) при планировании новых проектов, систем или процессов обработки ПДн.

Настоящий документ является DPIA для сервиса FitPulse и соответствует требованиям GDPR (ст. 35) и 152-ФЗ.

## 2. Описание системы обработки ПДн

### 2.1 Назначение системы
FitPulse — wellness-платформа, которая:
- Собирает и обрабатывает биометрические и медицинские данные пользователей.
- Генерирует персонализированные планы тренировок и питания на основе ML-моделей.
- Интегрируется с медицинскими сервисами и устройствами (wearables).
- Предоставляет доступ к данным через REST API и gRPC.

### 2.2 Типы обрабатываемых ПДн

| Категория | Примеры | Специальная категория? |
|---|---|---|
| Идентификационные данные | Email, имя, nickname | Нет |
| Биометрические данные | Параметры тела (вес, рост, % жира, мышечная масса), фотографии профиля | Да |
| Медицинские данные | Заболевания, симптомы, менструальный цикль, сон, питание | Да |
| Технические данные | IP-адрес, user-agent, device ID | Нет |
| Криптографические данные | Хеши паролей, TOTP-секреты, токены | Нет |

### 2.3 Объём обработки
- Активных пользователей: > 10,000 (ожидаемо на production).
- Записей ПДн в БД: > 1,000,000.
- Частота обработки: > 100 запросов/сек в пике.

## 3. Оценка необходимости и соразмерности

### 3.1 Необходимость обработки
| Данные | Необходимы для цели? | Минимизированы? |
|---|---|---|
| Email | Да (аутентификация, коммуникация) | Да |
| Имя/nickname | Да (персонализация) | Да |
| Параметры тела | Да (оценка состояния, план тренировок) | Да |
| Фотографии профиля | Нет (опционально) | Да |
| Менструальный цикл | Да (персонализация для женщин) | Да |
| Заболевания | Да (безопасность рекомендаций) | Да |
| IP-адрес | Да (безопасность, rate limiting) | Да |

### 3.2 Соразмерность
- Обработка специальных категорий ПДн (биометрические и медицинские) **необходима** для достижения целей сервиса и осуществляется с явного согласия субъекта.
- Минимизация: пользователь может отказаться от предоставления отдельных данных (например, фото профиля, заболеваний), что ограничит функционал, но не нарушит работу сервиса.

## 4. Оценка рисков для прав субъектов

### 4.1 Риск-матрица

| Риск | Вероятность | Влияние | Уровень риска | Действия |
|---|---|---|---|---|
| Утечка ПДн через SQL-инъекцию | Средняя | Высокое | Высокий | WAF, prepared statements, audit log |
| Компрометация БД | Низкая | Критическое | Высокий | Шифрование at rest, бэкапы, RBAC |
| Утечка через компрометацию аккаунта | Средняя | Среднее | Средний | MFA, rate limiting, audit log |
| Несанкционированный доступ персонала | Низкая | Высокое | Средний | RBAC, least privilege, quarterly access review |
| Утечка через third-party сервисы | Средняя | Среднее | Средний | Vendor audit, DPA, data minimization |
| DDoS-атака, приводящая к утечке | Средняя | Среднее | Средний | WAF, rate limiting, redundancy |

### 4.2 Детальный анализ рисков

#### Риск 1: Утечка ПДн через SQL-инъекцию
- **Вероятность**: Средняя (есть исторические прецеденты).
- **Влияние**: Высокое (доступ к email, именам, биометрическим данным > 10,000 пользователей).
- **Существующие меры**:
  - Использование prepared statements / pgx parameterized queries.
  - WAF (Cloudflare) с правилами SQLi.
  - Static analysis (gosec, govulncheck) в CI/CD.
  - Penetration testing раз в квартал.
- **Рекомендации**:
  - Добавить runtime SQL injection detection (например, PostgreSQL audit extension).
  - Обучение разработчиков secure coding.

#### Риск 2: Компрометация БД
- **Вероятность**: Низкая (ограниченный доступ к production).
- **Влияние**: Критическое (полная утечка всех ПДн).
- **Существующие меры**:
  - Шифрование at rest (pgsodium, pgcrypto).
  - Шифрование бэкапов.
  - RBAC в PostgreSQL (разделение ролей).
  - Audit logging всех операций с ПДн.
- **Рекомендации**:
  - PostgreSQL HA (Patroni + synchronous replicas) в Phase 2.
  - Transparent Data Encryption (TDE) в Phase 2.
  - Внешний аудит БД раз в квартал.

#### Риск 3: Утечка через компрометацию аккаунта
- **Вероятность**: Средняя.
- **Влияние**: Среднее (доступ к данным конкретного пользователя).
- **Существующие меры**:
  - MFA (TOTP).
  - Rate limiting (fail2ban, Valkey).
  - Audit logging всех входов.
- **Рекомендации**:
  - Обнаружение аномалий (unusual location, device) через ML.
  - Принудительный logout при подозрительной активности.

#### Риск 4: Несанкционированный доступ персонала
- **Вероятность**: Низкая.
- **Влияние**: Высокое (insider threat).
- **Существующие меры**:
  - RBAC (разделение на admin, user, auditor).
  - Least privilege principle.
  - Audit log с retention 3 года.
- **Рекомендации**:
  - Quarterly access review.
  - Обучение персонала по обработке ПДн.
  - Background checks для администраторов.

## 5. Субъекты ПДн и их права

### 5.1 Категории субъектов
1. **Клиенты**: пользователи сервиса, зарегистрированные через email/Google OAuth.
2. **Администраторы**: сотрудники с доступом к данным.
3. **Исследователи**: участники bug bounty program (не обрабатываем ПДн).

### 5.2 Права субъектов
- **Право на доступ**: `GET /api/v1/profile/export`.
- **Право на исправление**: `PUT /api/v1/profile`.
- **Право на удаление**: `DELETE /api/v1/profile`.
- **Право на портируемость**: export в JSON.
- **Право на ограничение обработки**: через support запрос.

### 5.3 Способы реализации прав
- Веб-интерфейс: раздел «Профиль».
- API: endpoints, описанные выше.
- Email: `privacy@fittpulse.ru`.
- Почтовый адрес: [указать при регистрации].

## 6. Меры защиты ПДн

### 6.1 Организационные меры
- Назначение ответственного за обработку ПДн.
- Обучение персонала.
- Политика доступности (NDA, onboarding).
- Incident response plan (см. `docs/compliance/ИНСТРУКЦИЯ_ПО_ИНЦИДЕНТАМ.md`).
- Vendor management (DPA с третьими сторонами).

### 6.2 Технические меры

#### Шифрование at rest
- **Пользовательские ПДн**: pgcrypto + pgsodium.
- **Пароли**: Argon2id.
- **TOTP-секреты**: pgsodium (libsodium secretbox).
- **Бэкапы**: LUKS / application-level шифрование.

#### Шифрование in transit
- **gRPC**: TLS 1.3.
- **HTTP**: TLS 1.3.
- **Внутренние вызовы**: mTLS.

#### Контроль доступа
- RBAC в приложениях и БД.
- MFA для администраторов.
- Audit logging всех действий с ПДн.

#### Мониторинг
- Elasticsearch + Kibana с retention 3 года.
- Alertmanager для аномалий.
- Prometheus + Grafana для метрик.

#### Сканирование
- Static analysis (gosec, govulncheck) в CI/CD.
- Сканирование секретов (Gitleaks, TruffleHog).
- Container scanning (Trivy).
- Penetration testing раз в квартал.

### 6.3 Аудит
- **Внутренний аудит**: quarterly access review, compliance check.
- **Внешний аудит**: ежегодный аудит 152-ФЗ compliance.
- **Audit log retention**: 3 года в Elasticsearch hot tier + archive in S3.

## 7. Оценка воздействия на права субъектов

### 7.1 Выводы
- FitPulse обрабатывает специальные категории ПДн (биометрические и медицинские), что требует повышенных мер защиты.
- Существует риск утечки ПДн, который минимизируется через шифрование, контроль доступа и мониторинг.
- Права субъектов ПДн реализованы через API endpoints и email support.
- Retention audit logs 3 года обеспечивает возможность ответа на запросы Роскомнадзора.

### 7.2 Рекомендации
1. **Обязательные (must-have)**:
   - Шифрование at rest для всех специальных категорий ПДн (выполнено).
   - Audit log retention 3 года (выполнено в документации, требуется настройка ELK).
   - Утверждение Политики обработки ПДн.
   - Назначение ответственного за обработку ПДн.

2. **Желательные (should-have)**:
   - PostgreSQL HA с синхронными репликами.
   - Внешний аудит compliance раз в год.
   - Обнаружение аномалий через ML.
   - Penetration testing раз в квартал.

3. **Опциональные (could-have)**:
   - DPIA обновление при изменении архитектуры.
   - Privacy by Design сертификация.
   - W3C Privacy CG участие.

## 8. Заключение

FitPulse обеспечивает соответствие требованиям 152-ФЗ и GDPR через:
- Шифрование ПДн at rest и in transit.
- Ограничение срока хранения ПДн.
- Аудит действий с ПДн с retention 3 года.
- Реализацию прав субъектов ПДн.
- Организационные и технические меры защиты.

DPIA требует регулярного обновления (при изменении архитектуры, законодательства или характера обработки ПДн).
