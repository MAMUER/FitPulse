# Инструкция по работе с инцидентами информационной безопасности

## 1. Назначение документа

Настоящая инструкция регламентирует порядок реагирования на инциденты информационной безопасности (ИБ), связанные с обработкой персональных данных (ПДн), в соответствии с требованиями 152-ФЗ, GDPR и внутренними политиками FitPulse.

## 2. Определения

- **Инцидент ИБ**: любое событие, которое может привести к компрометации конфиденциальности, целостности или доступности ПДн.
- **Команда реагирования на инциденты (IR Team)**: группа специалистов, ответственных за обнаружение, анализ, ликвидацию и документирование инцидентов.
- **PII (Personally Identifiable Information)**: информация, позволяющая идентифицировать субъекта.
- **Дата-брейч**: утечка ПДн, приведшая к несанкционированному доступу, раскрытию, изменению или уничтожению ПДн.

## 3. Классификация инцидентов

| Класс | Критерии | Примеры | Срок реакции | Уведомление РКН |
|---|---|---|---|---|
| **P0 (Critical)** | Утечка ПДн > 1000 записей, компрометация БД, доступ к PII у третьих лиц | SQL-инъекция, несанкционированный доступ к production БД, кража бэкапа | 1 час | Да, 72 часа |
| **P1 (High)** | Утечка ПДн < 1000 записей, компрометация одного аккаунта | XSS, CSRF, доступ к данным конкретного пользователя | 4 часа | Да, при наличии риска |
| **P2 (Medium)** | Риск утечки, попытка доступа, фишинг | Подозрительная активность, brute-force, фишинг-кампания против сотрудников | 1 рабочий день | Нет |
| **P3 (Low)** | Нарушение процедур, отсутствие контроля | Отсутствие MFA у администратора, устаревшие сертификаты | 5 рабочих дней | Нет |

## 4. Команда реагирования (IR Team)

| Роль | Обязанности | Контакт |
|---|---|---|
| **Incident Commander** | Координация, коммуникация, принятие решений | on-call engineer |
| **Forensic Analyst** | Сбор доказательств, анализ логов, сохранение цепочки custody | DevOps/Backend |
| **Communications Lead** | Уведомление субъектов, Роскомнадзора, прессы (при необходимости) | Legal/Compliance |
| **Security Engineer** | Техническое устранение уязвимости, патчи | Security |
| **DBA** | Восстановление данных, проверка БД на компрометацию | DBA/DevOps |

## 5. Процесс реагирования на инциденты

### 5.1 Обнаружение (Detection)

Источники обнаружения:
- **Автоматические алерты**: Prometheus + Alertmanager, logs-based алерты.
- **Penetration testing**: регулярные пентесты.
- **Bug bounty**: сообщения от исследователей.
- **Мониторинг**: SIEM, EDR, WAF logs.
- **Сотрудники**: внутренние каналы reporting.

### 5.2 Анализ (Analysis)

1. **Сбор информации**:
   - Время обнаружения инцидента.
   - Аффектированные системы и данные.
   - Характер воздействия (чтение, изменение, удаление).
   - Количество затронутых субъектов.

2. **Определение класса инцидента** (см. раздел 3).

3. **Сбор доказательств**:
   - Дампы логов из Elasticsearch (retention 3 года).
   - Network traces (tcpdump, istio telemetry).
   - Database audit logs.
   - Snapshot затронутых подов/volumes (не отключать evidence!).

### 5.3 Сдерживание (Containment)

1. **Изоляция затронутых систем**:
   - Отключение компрометированного пода/сервиса.
   - Блокировка подозрительных IP/account.
   - Приостановка интеграций (если компрометация затрагивает третьи стороны).

2. **Сохранение цепочки custody**:
   - Все действия фиксируются в audit log с временными метками.
   - Изменения в системе фиксируются через git commit и change management.

### 5.4 Устранение (Remediation)

1. **Удаление уязвимости**:
   - Патчи, обновления зависимостей.
   - Изменение конфигураций (например, закрытие портов, обновление WAF rules).

2. **Восстановление систем**:
   - Восстановление из бэкапа (если данные повреждены/удалены).
   - Перегенерация секретов (пароли, токены, сертификаты).

3. **Проверка на persistence**:
   - Поиск backdoor, web shell, persistence mechanism.
   - Проверка cron jobs, systemd services, k8s cronjobs.

### 5.5 Восстановление (Recovery)

1. **Постепенный возврат в production**:
   - Сначала на staging/clone окружении.
   - Мониторинг метрик (latency, error rate, audit log).
   - Полный rollout после подтверждения безопасности.

2. **Уведомление затронутых субъектов**:
   - Письмо на email с описанием инцидента, затронутых данных, предпринятых мерах.
   - Рекомендации по действиям субъектов (смена пароля, проверка активности).
   - Если инцидент затрагивает > 1000 субъектов — уведомление Роскомнадзора в течение 72 часов.

### 5.6 Постинцидентный анализ (Post-Mortem)

1. **Root Cause Analysis (RCA)**:
   - Определение корневой причины (человеческий фактор, ошибка в коде, недостатки инфраструктуры).
   - Timeline инцидента от обнаружения до устранения.

2. **Документирование**:
   - Отчёт в формате blameless post-mortem.
   - Хранение отчёта в репозитории (без чувствительных данных).

3. **Ретроспектива**:
   - Обсуждение на weekly sync.
   - Создание action items для предотвращения повторения.

## 6. План реагирования на типовые сценарии

### 6.1 SQL-инъекция / Несанкционированный доступ к БД

1. **Detect**: WAF alert, SQL error spike, anomaly detection в audit log.
2. **Contain**: Отключение сервиса, блокировка attacker IP, отключение публичного доступа к БД.
3. **Remediate**: Патч уязвимости, rotation всех паролей/ключей, проверка integrity данных.
4. **Notify**: РКН (если > 1000 записей), затронутые субъекты, регулятор (если требуется).
5. **Post-mortem**: Анализ WAF logs, code review, penetration test.

### 6.2 Компрометация аккаунта администратора

1. **Detect**: Аномальная активность (unusual IP, time, action).
2. **Contain**: Блокировка аккаунта, отзыв всех токенов, принудительный logout.
3. **Remediate**: Сброс пароля, MFA re-enrollment, проверка действий администратора.
4. **Notify**: Если доступ был к ПДн субъектов — уведомление РКН.
5. **Post-mortem**: Анализ логов, причинно-следственная цепочка.

### 6.3 Утечка через сторонний сервис

1. **Detect**: Bug bounty report, third-party notification.
2. **Contain**: Оценка объёма утечки, изоляция затронутых данных.
3. **Remediate**: Отзыв доступа к стороннему сервису, обновление интеграций.
4. **Notify**: Зависит от объёма и характера утечки.
5. **Post-mortem**: Оценка рисков третьих сторон, пересмотр vendor management.

### 6.4 DDoS-атака

1. **Detect**: Спайк latency, error rate, traffic spike.
2. **Contain**: Включение Cloudflare Under Attack Mode, rate limiting.
3. **Remediate**: Блокировка malicious IP, масштабирование.
4. **Notify**: Если привело к утечке ПДн — по сценарию 6.1.
5. **Post-mortem**: Анализ атаки, улучшение WAF rules.
