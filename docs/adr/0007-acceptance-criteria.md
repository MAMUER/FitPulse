# ADR 0007: Критерии приёмки архитектуры (Definition of Done)

## Статус

Принято

## Контекст

Архитектура должна соответствовать определённым критериям по доступности, производительности, масштабируемости, устойчивости, безопасности, compliance и документации, чтобы считаться production-ready.

## Решение

Определить критерии приёмки:

1. **Доступность**: >99.9% uptime annually, мониторинг через Prometheus probes и Telegram-алерты. Синтетические транзакции не реализованы.

2. **Производительность**: p95 latency <5s для 95% пользовательских запросов, измерение через гистограммы Prometheus. Alertmanager алерт `HighLatency` срабатывает при p95 > 0.5s. RUM (Real User Monitoring) не реализован. Исключение для ML-эндпоинтов: <15s с уведомлением пользователя.

3. **Масштабируемость**: автоскейлинг при 2x нагрузке → 2x подов за 3 минуты с помощью HPA (min 2, max 5 replicas для core-сервисов). Cluster Autoscaler не реализован. Тестирование через k6 нагрузочные тесты в CI (`load-test.k6`, `scripts/load-test.py`).

4. **Устойчивость**: восстановление после сбоя <5 минут вручную (manual rollback через `kubectl rollout undo`). Chaos Engineering (pod kills, network partitions) запланирован на Phase 2. MTTR трекается в Grafana.

5. **Безопасность**: 0 критических уязвимостей после пентеста. Квартальные внешние пентесты и ежемесячные внутренние сканирования запланированы на Phase 2. Текущие меры: автоматические SAST/DAST (Trivy, govulncheck, gosec, semgrep, CodeQL, Gitleaks, TruffleHog, Checkov, Kubescape, kube-hunter) в CI/CD. SLA remediaton (best effort, без юридических гарантий: critical — 1–3 рабочих дня, high — 3–7 рабочих дней).

6. **Compliance**: полное соответствие 152-ФЗ при обработке персональных данных. Хранение в России (требует размещения на хосте в РФ), шифрование at rest/transit, механизмы реализации субъективных прав, регистрация в Роскомнадзоре. Ежегодные аудиты, DPIA для новых фич. Централизованный audit trail в Elasticsearch запланирован на Phase 2.

7. **Документация**: актуальная документация репозитория, включая ADRs, runbooks, incident playbooks, OpenAPI спецификации (`api/rest/swagger.yaml`). Документация обновляется в том же PR, что и код.

## Последствия

- предоставляет чёткие, измеримые цели для качества архитектуры;
- обеспечивает соответствие системы бизнес- и регуляторным требованиям;
- облегчает объективную оценку архитектурных решений.

## Реализация

- реализован мониторинг и алертинг для доступности и производительности (Prometheus probes, гистограммы latency, Alertmanager с Telegram);
- k6 нагрузочные тесты реализованы и запускаются в CI (`load-test.k6`, `scripts/load-test.py`);
- Chaos Engineering и внешние пентесты запланированы на Phase 2;
- поддерживаются стандарты документации и процессы review.

## Рассмотренные альтернативы

- Меньше критериев: может привести к низкому качеству.
- Субъективные критерии: сложно измерить и применить.
- Отсутствие формальной приёмки: риск неполных реализаций.
